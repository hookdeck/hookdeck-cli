# hookdeck-cli v3.0.0

Paste this into the GitHub Release when cutting `v3.0.0`. `CHANGELOG.md` is unmaintained and
points at GitHub Releases, so this file is the source rather than a changelog entry.

The reasoning behind these changes, the alternatives rejected and the evidence for each decision
are in [`mcp_read_write_tool_split.md`](./mcp_read_write_tool_split.md).

---

## Summary

v3.0.0 brings **Outpost to the command line**. `hookdeck outpost` manages tenants, destinations and
the events delivered to them, publishes events, inspects delivery attempts, and reads topics,
destination types, metrics, operator config and deployment status — with `hookdeck outpost mcp`
exposing the same surface to an AI agent. Every Outpost command is marked **[BETA]**: they work
against the live API, and the flags and output may still change.

The other half of the release is that the MCP servers can now change things. Every Event Gateway
tool was read-only in v2.6.0; create, update, delete, retry, cancel, mute and dismiss are all
available in v3.0.0, behind `--allow-write`. Rather than hang those actions off the tool names you
already grant, each resource splits into a `_read` half and a `_write` half — MCP clients grant
permission per tool name, with no way to match on arguments, so a name carrying both `list` and
`delete` has to be allowed or denied whole. With the split, **"allow all reads, prompt on anything
that changes data" is a single rule**: `mcp__hookdeck-gateway__*_read`. It could not be expressed
at all before.

That costs you one re-grant. The Event Gateway tools also move from the `hookdeck_*` prefix to
`gateway_*`, and both renames land together deliberately — splitting later would have meant asking
you to do this twice.

Alongside it are two smaller breaking changes and a long list of fixes, most of them the same shape
as v2.5.0 and v2.6.0: the CLI or the MCP server reported success while quietly doing something
other than what you asked. An ignored filter returning everything. A `--hookdeck-config` honoured
for reads and ignored for writes. A mistyped subcommand exiting 0.

If you have automation built against v2.x, the three breaking changes below are the ones to check.

## Breaking: every MCP tool has been renamed

Product tools move from `hookdeck_*` to `gateway_*`, and each tool splits by what it does:

```
gateway_connections  ->  gateway_connections_read   list, get
                         gateway_connections_pause  pause, unpause
                         gateway_connections_write  create, upsert, update, delete, enable, disable
```

Outpost splits the same way — `outpost_tenants_read` / `_write`, `outpost_destinations_read` /
`_write`, and so on. `hookdeck_login` keeps its prefix, and `hookdeck_projects` becomes
`hookdeck_projects_read` and `hookdeck_projects_use`.

**Per-tool permission grants and `allowedTools` entries need updating once.** They do not survive a
rename and MCP has no migration mechanism, so an agent that was working will stop until you
re-grant.

Two mutations deliberately keep their own tool rather than moving to `_write`:
`gateway_connections_pause`, because read-only MCP is the incident-investigation tool and pausing a
misbehaving connection is the natural end of an investigation, and `hookdeck_projects_use`, which
changes what every other tool returns without writing project data.

**Arguments an action ignores are now refused.** Every property is scoped to the actions whose
handler reads it, so `{"action": "get", "order_by": "created_at"}` returns an error naming
`order_by` instead of succeeding and dropping it. That was the point of the split: an ignored
filter makes **a result look filtered when it is not**. Calls that previously worked while
discarding an argument now fail, and the error says which action does accept it.

**Declared enums are now enforced.** They never were — a value outside a property's declared set
went straight to the API. An invalid value that used to fail at the server now fails locally,
naming what is accepted.

## Breaking: `--hookdeck-config` writes the file it names

The flag was honoured for reads and ignored for writes. Run from any directory containing
`.hookdeck/config.toml`, `hookdeck project use` wrote to **that** file rather than the one you
named, reported success, and the next command disagreed with it:

```sh
$ hookdeck --hookdeck-config ./explicit.toml project use "Acme" "Second project"
Successfully set active project to: Acme / Second project
Updated: ./.hookdeck/config.toml          # not the file you named

$ hookdeck --hookdeck-config ./explicit.toml whoami
Logged in as ... on project First project  # disagrees with the line above
```

`--hookdeck-config` is how you keep a command off your own configuration, which is exactly what it
was failing to do. Precedence is now explicit and applies to reads and writes alike: the flag names
the file, `--local` means `./.hookdeck/config.toml`, and with neither the CLI uses a cwd-local
config if one exists and the global config otherwise. Passing both is still an error.

`HOOKDECK_CONFIG_FILE` has the same effect as the flag, and the flag wins if both are set. One
asymmetry is deliberate and documented in `REFERENCE.md`: only the flag is rejected alongside
`--local`.

If you pass `--hookdeck-config` from a directory that happens to contain `.hookdeck/config.toml`,
a different file changes now than before.
([#424](https://github.com/hookdeck/hookdeck-cli/issues/424))

## Breaking: an unknown subcommand now fails

An unknown subcommand of a group command printed that group's help and **exited 0**:

```sh
$ hookdeck gateway connection lst
<prints `hookdeck gateway connection` help>
$ echo $?
0
```

It now names the command and exits 1:

```sh
$ hookdeck gateway connection lst
Unknown command "lst" for "hookdeck gateway connection". Did you mean "list"?
$ echo $?
1
```

A script that ran a mistyped or non-existent subcommand was getting a success code and no error, so
the failure surfaced later as missing work rather than at the call. Only the root command reported
unknown commands before; this now applies to all 23 group commands. A bare group command —
`hookdeck project`, `hookdeck outpost tenant` — still prints its help and exits 0.

## New features

- **Outpost support — `hookdeck outpost …` [BETA].** A command group covering the managed Outpost
  API: `tenant`, `destination`, `destination-type`, `event`, `attempt`, `publish`, `topic`,
  `metrics`, `config` (including the tenant portal custom domain) and `status`.

  ```sh
  hookdeck outpost tenant upsert acme
  hookdeck outpost destination create --tenant-id acme --type webhook \
    --config url=https://acme.example.com/hooks --topics orders.created
  hookdeck outpost publish --tenant-id acme --topic orders.created --data '{"id": "ord_1"}'
  hookdeck outpost attempt list --event-id <id>
  ```

  A destination's fields belong to your Outpost deployment rather than to the CLI, so they are
  repeatable `--config key=value` and `--credential key=value` pairs rather than a flag per field,
  with `--config-file` and `--credentials-file` as escape hatches. A dotted key builds a nested
  object — `--config a.b=c`, following Helm's `--set` — so a nested field added server-side does
  not need a CLI release before you can use it. The CLI fetches each type's schema and refuses
  unknown keys, missing required fields, and values outside a declared option set or pattern before
  sending anything, naming the flag to fix.

  Because `--config` alone cannot tell you which keys a type accepts,
  `hookdeck outpost destination create --type <type> --help` lists that type's fields, read from
  the same schema and served from a 24-hour cache. Plain `--help` is unchanged and needs neither
  network nor credentials. `hookdeck outpost destination-type list|get` is the same information as
  a command.

  `--metadata key=value` and `--metadata-file` are on destination `create` and `update` as well as
  `tenant upsert`, so metadata of your own is reachable from the CLI and not only through an agent.

  Every command requires an Outpost project; the CLI refuses to run them against an Event Gateway
  project rather than returning confusing 404s. `publish` needs a Project API key, which the
  credentials stored by `hookdeck login` cannot substitute for — pass `--api-key` or set
  `HOOKDECK_API_KEY`. ([#346](https://github.com/hookdeck/hookdeck-cli/issues/346),
  [#347](https://github.com/hookdeck/hookdeck-cli/issues/347))

- **`hookdeck outpost mcp` [BETA]** — an MCP server over the same surface:
  `outpost_tenants_read` / `_write`, `outpost_destinations_read` / `_write`,
  `outpost_events_read` / `_write`, `outpost_config_read` / `_write`, `outpost_attempts_read`,
  `outpost_topics_read`, `outpost_destination_types_read`, `outpost_metrics_read`,
  `outpost_status_read` and `outpost_publish_write`, alongside `hookdeck_login`,
  `hookdeck_projects_read` and `hookdeck_projects_use`. It follows the same `_read` / `_write`
  split as the Event Gateway server, so the one permission rule covers both.

  It starts read-only, and the gate is the schema rather than a runtime check: a write tool is
  absent from `tools/list` entirely rather than registered to fail, so an agent is never told
  about something it cannot do. `--allow-write` enables the rest and is also read from
  `HOOKDECK_MCP_ALLOW_WRITE`, with the flag winning; `--read-only` is accepted and wins over both.

  Two actions that only read are gated with the writes. `token` mints a tenant-scoped access token
  and `portal` returns a URL granting access to a tenant's portal — both hand back a **reusable
  credential**, so a split drawn on HTTP methods alone would leave a read-only session able to
  produce them at will.

  Publishing has its own credential: `--publish-api-key`, or `HOOKDECK_OUTPOST_PUBLISH_API_KEY`.
  `HOOKDECK_API_KEY` is deliberately not read here — it means "exchange this for CLI credentials"
  everywhere else and is commonly exported in CI, and an ambient variable should not quietly
  register the one tool whose effects cannot be undone. Without a key the publish tool is not
  registered, and `outpost_help` explains why.

- **The Event Gateway MCP server can now change data, behind `--allow-write`.** Every tool shipped
  read-only in v2.6.0; the API client had the methods, the tool layer never offered them. Now
  available: `create`, `upsert`, `update`, `delete`, `enable` and `disable` on connections, sources
  and destinations; `create`, `upsert`, `update` and `delete` on transformations; `retry`, `cancel`
  and `mute` on events; `retry` on requests; `update` and `dismiss` on issues. Enable with
  `--allow-write` or `HOOKDECK_MCP_ALLOW_WRITE=true`; `--read-only` is accepted and wins if both
  are passed.

  `pause` and `unpause` stay available without it, on `gateway_connections_pause`. Read-only is the
  mode you investigate an incident in, and stopping a misbehaving connection is the natural end of
  an investigation — both are reversible, and pausing buffers delivery rather than dropping events.
  `run` on `gateway_transformations_read` is a read for the same kind of reason: checked against the
  API, a run creates no execution record, changes no transformation and delivers nothing, and
  without it a read-only session can read transformation code but never test it against a payload.

- **`gateway_bulk_read` and `gateway_bulk_write`** — bulk retry, cancel and replay across five
  operations. `plan` estimates what an operation would touch **without running it**, and it is a
  read, so you can size the blast radius with no write access at all. Filters are validated locally
  against what each operation declares, because the API ignores a filter it does not recognise —
  and an ignored filter on a bulk retry means running across everything the rest matched. Fifteen
  of the nineteen bulk endpoints have never been reachable from the CLI or an agent before.

- **Events and requests split into a plural search tool and a singular by-id tool.**
  `hookdeck_events` carried six actions and 25 parameters and `hookdeck_requests` six and 19, but
  only `id` was shared — every other parameter was a list filter, so `retry`, `cancel` and `mute`
  each needed one argument and were shown all of them:

  ```
  gateway_events_read     list, list_ignored — and the filters
  gateway_event_read      get, raw_body          gateway_event_write     retry, cancel, mute
  gateway_requests_read   list — and the filters
  gateway_request_read    get, raw_body          gateway_request_write   retry
  ```

  **The `events` and `ignored_events` actions on the old `hookdeck_requests` have moved.** A
  request's events are now `gateway_events_read` with a `request_id` filter, and its ignored events
  are the `list_ignored` action on the same tool. `GET /requests/{id}/events` is the only
  relationship traversal the API offers, so there is no `event_id` filter on requests going the
  other way, and the tool descriptions say so rather than leaving an agent to hunt for one.

  Guessing wrong recovers rather than dead-ends. Asking a singular tool to `list` names the plural
  tool in the error, and the other way round. An id of the wrong kind is caught before the call —
  Hookdeck ids carry their type as a prefix, so a `req_` id handed to the event tool is told what it
  is and which tool takes it, instead of coming back `Resource not found` and being reported as a
  request that does not exist.

- **Documented query filters that neither the CLI nor the MCP tools exposed.**
  `hookdeck gateway requests list` gains `--search-term`, `--events-count`, `--ignored-count` and
  `--cli-events-count`. `hookdeck gateway events list` and `hookdeck gateway request events` gain
  `--search-term` and `--next-attempt-at-after` / `--next-attempt-at-before`. The same filters are
  on `gateway_requests_read` and `gateway_events_read`.

  Two of them answer questions that had no answer at all. `--events-count 0` finds requests that
  produced no events, which is the usual explanation for a webhook that appears to have gone
  missing. `--search-term` matches a value across body, headers, parsed query and path at once, for
  when you know the value but not which field carries it — it matches a whole value, not a
  substring.

## Fixes

### MCP

- **Debug logs no longer persist credentials.** Redaction matched one top-level request field and
  did not run over responses at all, so an Outpost destination's nested `credentials`, an API key
  create's secret, a tenant token and a webhook destination's signing secret were **written
  verbatim to disk** by anything run with `--log-level debug`, CLI command or MCP server alike.
  Redaction is now recursive by field name and covers responses and response headers as well as
  requests, and the header list covers `X-Api-Key`, `Set-Cookie`, `Cookie` and
  `Proxy-Authorization` rather than `Authorization` alone.

- **A filter sent as the wrong JSON type is no longer thrown away.** Models routinely emit numbers
  and booleans as strings, and the reverse. `verified: "false"` and `limit: "5"` were discarded
  because the accessors took a bare type assertion, and `events_count: 0` — a JSON number, which is
  the natural way to send a count — was discarded because that property is typed `string` to allow
  operator syntax. None of it errored: **the API returned everything and the caller reported an
  unfiltered answer as a filtered one**, so `gateway_requests_read {"verified": "false"}` listed
  every request and called them all unverified. Both directions now convert, and a value nothing
  can parse is refused rather than guessed at.

- **Argument values a tool cannot use are refused rather than dropped.** The input helpers
  discarded what they could not convert, so `{"topics": ["orders", 5]}` subscribed a destination to
  **one** topic and reported success. A non-string inside a string array, and an array where a
  single value belongs, are now errors. The deliberate conversions are untouched: a
  comma-separated string still stands in for an array, and numbers and booleans still work as
  strings.

- **Enabling writes no longer reopens the ignored-filter hole.** A write-only property was hidden —
  and therefore refused — in read-only mode, but `--allow-write` made it visible on every action,
  so a read action accepted an argument it never reads and ignored it.
  `gateway_sources_read {"action": "list", "type": "STRIPE"}` returned all 70 sources, none of them
  Stripe, with no error. A write-only property is now refused on an action that does not write,
  whatever the mode, and the message names the actions that do take it.

- **`gateway_connections_read` no longer answers a `disabled` filter it cannot honour.**
  `disabled: false` was accepted and ignored, returning every connection as though filtered to the
  enabled ones. Verified against the API with a disabled connection present, there is no
  enabled-only filter to send — `disabled_at[any]` selects disabled connections whatever value it
  is given and `disabled_at[is_null]=true` returns everything — so the argument is now refused with
  that explanation rather than answered wrongly in either direction.

- **`gateway_metrics_read` rejected the `measures` it had just been given.** It was the one place
  on the surface reading a list with a strict array accessor, so the comma-separated form every
  other tool accepts was dropped and you were told `measures is required` for an argument you had
  supplied.

- **A tool offering `pause` no longer advertises itself as a pure read.** `ReadOnlyHint` was
  derived from whether any action was gated, and pause and unpause are deliberately ungated, so
  `gateway_connections` claimed `readOnlyHint: true` while offering them — **a client that
  auto-approves read-only tools would have halted production delivery without asking anyone.**
  Gating and annotation are now separate questions.

- **Read-only mode no longer describes what it has taken away.** The action enum was filtered by
  mode but nothing else was, so `gateway_event_read` said "read the event, get its payload, retry,
  cancel or mute it" over an enum of `[get, raw_body]` — and prose is more persuasive to a model
  than a schema. Help topics rendered the unfiltered property list too, so an agent got a different
  parameter set depending on where it looked. One decision now feeds the schema and the help, and
  the Outpost tools mark their write-only properties, which they never had: read-only Outpost
  sessions were offered `config`, `credentials`, `filter`, `metadata`, `values`, `unset`,
  `hostname` and `theme`. ([#363](https://github.com/hookdeck/hookdeck-cli/issues/363))

- **`gateway_connections_write` could not create a connection without an explicit `rules` array.**
  `rules` is optional and the CLI equivalent works without it, but an absent key reached the API as
  `"rules": null` and came back `rules must be an array` — so the most obvious first call against
  the new write tool failed. An explicit `[]` still reaches the API and clears the ruleset.
  ([#425](https://github.com/hookdeck/hookdeck-cli/issues/425))

- **Help text and error hints named tools that do not exist.** `gateway_help` told you to call
  `hookdeck_projects`, which the split had removed, so following the help returned `unknown tool`.
  The pre-startup auth error in an Outpost session said to call `outpost_login`, which no server
  registers — signing in is a platform operation, so both servers register `hookdeck_login`
  whatever their product prefix, and the one message whose job is to say what to do next named a
  tool the agent could not call. A guard now reads every tool name mentioned in text an agent sees
  and requires the server to advertise it.
  ([#426](https://github.com/hookdeck/hookdeck-cli/issues/426))

- **Bulk queries take `connection_id`**, like every other tool, rather than the API's `webhook_id`.
  A refusal now names the filter you typed instead of the wire name you did not — previously even
  the rejection advertised `webhook_id`, a token that appeared nowhere in the call.
  ([#427](https://github.com/hookdeck/hookdeck-cli/issues/427))

- **A browser login can no longer attach a server to the wrong product's project.** An Outpost MCP
  server could complete login on a Gateway project and adopt it, after which every call reached a
  product that does not serve it and returned 404 — **data that reads as missing** rather than a
  project that was never right. The login is refused before anything is saved, and the error says
  so.

- **An abandoned re-authentication no longer signs you out.** `hookdeck_login` with `reauth: true`
  deleted the stored credentials before opening the browser flow. A completed sign-in rewrites
  every field, so clearing first gained nothing on the path that works — it only had an effect on
  the path that does not, where a closed laptop or a failed poll left you signed out of **every
  terminal and every future session** with nothing to show for it. The in-memory clear is
  unchanged, and `hookdeck logout` still removes the file.

- **`outpost_destinations_write` could not create a destination without being told `topics`.** The
  field was dropped when absent and the API answered 422. The CLI has always defaulted an omitted
  `--topics` to everything, because the API requires the field; the tool now does the same.
  `update` is untouched, where an absent `topics` still means "leave them alone".

- **`gateway_transformations_read run` reported nothing for a run that failed.** The response
  carried neither `log_level` nor `console`, so a syntax error, a throwing handler and a clean run
  were indistinguishable — all three returned `{"data": {}}`. A failed run is now an error carrying
  the console output, so you see `Error: boom` rather than an empty object. The MCP path also sent
  no content-type, which the engine requires while the schema says headers may be an empty object,
  so following the documentation produced a failure nothing explained and identical code worked
  from the CLI.

- **`outpost_events_write` accepted `tenant_id` on `retry` and issued the retry anyway**, while you
  believed it was scoped to that tenant.

- **The connections tools said "id or name is required" to callers who had just passed `name`.**
  `id` accepts a name, but only `id` was read — and `name` is a declared property, so reaching for
  it was the obvious move and the obvious move dead-ended. Both are now read. The destinations
  tools separately offered type `MOCK` in their summary while the property and the API both take
  `MOCK_API`, and the summary is what a model weights most.

- **`outpost_tenants_write` did not validate `theme`.** The CLI rejected `--theme purple`; the MCP
  tool returned a portal URL. Both now read one list of accepted themes — and declared enums are
  enforced generally now, which they never were.

- **Outpost tool descriptions promised arrays the validator refuses.** Thirteen properties said
  they accepted an array or a comma-separated string while the schema declared a string, so the
  documented form was rejected before the handler that would have split it ever ran.

- **Write tools advertised read-only parameters** such as `limit`, `next` and `prev`, and 91
  property descriptions named actions their tool does not have — `gateway_connections_pause` said
  its `id` was "Required for get, pause, unpause, update, delete, enable and disable" on a tool
  offering two of those, and `outpost_events_write.id` explained what happens "on list".
  ([#363](https://github.com/hookdeck/hookdeck-cli/issues/363))

- **The `mcp --help` smoke-test example did not work.** Piping a single JSON-RPC request printed
  nothing and exited non-zero, because the server exits on EOF and `echo |` closes stdin before the
  reply is written. ([#428](https://github.com/hookdeck/hookdeck-cli/issues/428))

### Outpost

- **`hookdeck outpost publish` no longer reports success for a tenant it cannot reach.** The API
  accepts an unknown tenant with a 202 and an event id; the event then matches no destination, is
  never delivered, and appears in no event list. The CLI printed a green tick, exited 0, and the
  only hint was `No destinations matched this topic`, which blames the topic when the tenant is
  what is wrong. Publishing follows the `--api-key` credential rather than the active project, so
  this also fires when the key belongs to a different project than the one you are working in —
  the case the message now names. A lookup that itself errors still lets the publish through, since
  refusing over a transient failure would be worse than the problem being guarded against.

- **Publishing through MCP checked the credential's project, not yours.** The publish credential is
  fixed when the server starts while the active project moves with `hookdeck_projects_use`. When
  they disagreed, publishing for a tenant that existed in the active project was accepted with a
  202 and an event id, **matched nothing, was never delivered, and appeared in no event list** —
  and the response reported the active project in its `meta`, which read as confirmation that the
  event had landed where you were looking. A publish that matches no destination now carries a
  warning rather than looking like an ordinary success.

- **`hookdeck outpost destination update` can change one field.** It applied create-time validation
  to a merge-patch endpoint, so supplying any config or credential made it enforce the type's
  required fields against just those values. Rotating a credential —
  `destination update des_x --tenant-id acme --credential secret=new` — failed client-side with
  `--config url=<value> is required` before a request was sent, so **rotation was impossible from
  the CLI** while the MCP path, which validates nothing, worked. Required fields are enforced on
  create only; unknown keys, option sets and patterns are still checked on update.

- **A new destination now gets the defaults its own help advertises.** The destination-type schema
  publishes a default per field and the CLI prints it (`tls … default: on`), but nothing sent it,
  and the API treats an absent key as unset rather than applying the default itself. Following the
  CLI's own printed example for a `rabbitmq` destination stored `tls: "false"` — **the connection
  carried its SASL credentials in the clear.** Same for `kafka`. Defaults are now filled in for
  fields you did not supply, on the CLI and through MCP, and the applied values are printed to
  stderr: turning TLS off should be something you see.

- **Values you supplied are no longer dropped on the way to the API.** `outpost publish --data '{}'`
  sent no data at all and then failed with `data is required` for a payload you had given it.
  `outpost destination update --filter '{}'` could not clear a filter: the API replaces `filter`
  wholesale so an empty object clears it, but an empty map marshalled to nothing, changed nothing,
  and reported success.

- **`outpost event retry` and `outpost destination enable|disable` report what happened, not what
  was asked.** Retry printed a success tick without reading the response's success flag, and its
  MCP sibling reported `status: "queued"` even when the retry was declined; enable and disable
  announced the verb without checking the state that came back.

- **Outpost API errors are readable.** An error body whose `data` member is an object failed to
  decode, so the whole envelope was handed to you as raw JSON with the readable sentence buried
  inside it — the shape used for not-found and for several rejected-value errors, so it covered a
  large share of the errors anyone actually hits. Separately, `{"message": "validation error",
  "data": ["topic is invalid"]}` surfaced as a bare `validation error` because only `message` was
  parsed; the detail is now appended, which improves every Outpost command.

- **`hookdeck outpost tenant portal` explains a project with no portal.** The API answers 404,
  which reads as a missing tenant. It now names the precondition its own help already documents,
  and the command that fixes it.

- **An outpost command on the wrong project no longer sends you round a loop.** It said to run
  `hookdeck project use`; with a project-scoped credential that command refuses and says to sign in
  again, and signing in with the same key lands back on the original error — three commands, no way
  out, on the path every new user takes. The guard now establishes whether your credential can
  switch projects at all before advising, and when it cannot, names the two things that do work.

- **`--metadata` on `outpost destination update` merges, and the help now says so.** It documented
  wholesale replacement — verified against the API, including a direct call, the endpoint merges —
  and an empty `--metadata-file` reported success while sending nothing. Clearing is now refused
  with the reason rather than quietly accepted.

- **A rejected `--api-key` on `outpost publish` says what kind of key it wants.** The generic 401
  text told you to run `hookdeck login`, which produces exactly the kind of credential the publish
  API refuses — as the command's own help says two paragraphs earlier.

### CLI

- **`hookdeck ci --help` and `hookdeck outpost publish --help` no longer print your API key.**
  `--api-key` used the value of `HOOKDECK_API_KEY` as its pflag default, and pflag prints a
  non-empty string default, so with the variable exported the key was **echoed into the terminal,
  the scrollback and any log that captured it**:

  ```sh
  $ export HOOKDECK_API_KEY=<your key>
  $ hookdeck ci --help
        --api-key string   Your Hookdeck Project API key. The CLI reads from HOOKDECK_API_KEY
                           if not provided. (default "<your key, in full>")
  ```

  `tools/generate-reference` reads the same flag defaults, so running it with the variable set
  would have written the key into `REFERENCE.md`, which is public. Both commands now declare an
  empty default and read the variable at run time; the flag still wins over the environment.

- **A resource id can no longer retarget a request at a different resource.** Ids reached the API
  client from command arguments and MCP tool calls and were concatenated straight into URL paths,
  and resolving a path against the base URL normalises `..` — so an id like
  `src_1/../../destinations/des_2` produced a valid URL for **a different resource of a different
  type**, while the caller went on reporting the id it had been given, so neither the output nor a
  transcript showed what was actually addressed. Each caller-supplied segment is now validated and
  escaped, and the request layer checks the resolved URL before sending.

- **`gateway event retry|cancel|mute` report the status the API returned.** All three discarded the
  response body and reported success from the status code alone — but the API answers 200 to a
  no-op, so cancelling an already-delivered event leaves it `SUCCESSFUL` and the CLI printed
  `Event … cancelled.` anyway. You now get `Event evt_x is now SUCCESSFUL.`, and the MCP tool
  returns the event rather than a hardcoded `"status": "cancelled"`.

- **`gateway request retry` says how many events it produced.** A retry aimed at a connection the
  request never went through is accepted and creates nothing; the CLI printed `retry requested` and
  the MCP tool answered `{"status": "retried"}` either way. The CLI now fails when a retry created
  no events, and names the count when it did.

- **`gateway issue dismiss` says what it changed.** Two independent QA passes reported "dismiss
  does not dismiss" after checking `status` and finding it unchanged. Nothing was broken —
  dismissal and resolution are separate axes, and the API populates `dismissed_at` while leaving
  `status` alone — so nothing changed except what is said: the CLI now names `dismissed_at` and
  states that `status` is unchanged.

- **`gateway connection update --rules '[]'` clears a ruleset.** The API replaces `rules` wholesale
  so an empty array removes them all, but an empty slice marshalled to nothing: the command changed
  nothing and exited 0.

- **A 401 in a terminal no longer tells you to call an MCP tool.** The generic authentication error
  appended `MCP: use hookdeck_login with reauth: true` wherever it was printed, including to a
  reader with no way to call a tool. That line now goes only to an actual MCP session.

- **A warning could corrupt `--output json`.** Source validation warned on **stdout** when the
  OpenAPI spec fetch failed, so the warning landed ahead of the JSON and you got
  `invalid character 'W' looking for beginning of value`. That fetch fails only intermittently, so
  it broke scripts at random rather than consistently. Warnings now go to stderr.

## Not in this release

**Platform management is not included.** Organization get/update, project CRUD, custom domains and
organization API keys were built and then parked: every platform API route requires an organization
API key, so these would answer "Unauthorized" to anyone using an ordinary CLI session. The work is
preserved on the
[`platform-api`](https://github.com/hookdeck/hookdeck-cli/tree/platform-api) branch pending a
decision on the permission model. `hookdeck project list` and `hookdeck project use` are unaffected.

**API key management is not available through MCP, in any form.** A key is a credential, and an
agent able to mint one could grant itself access the server would otherwise refuse. Use the
dashboard.
